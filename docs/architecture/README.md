# Architecture

One request, from a Flutter widget to a SQLite row and back, and what is
generated along the way.

- [Backend module structure](backend-structure.md) — where server code goes.
- [Mobile module structure](mobile-structure.md) — where client code goes.

## The path of a request

```text
CatalogPage            widget: renders state, decides nothing
  ↓ read/watch
CatalogViewModel       state machine: loading → ready | failed
  ↓ calls
CommerceApi            GENERATED from an annotated interface
  ↓ HTTP, JSON encoded by the shared models
Router                 dust_server, hand-written
  ↓
handler/list.dart      parses the request, shapes the answer
  ↓
service/list.dart      the rules: what is published, what it costs
  ↓
CatalogRepository      GENERATED from @Query, SQL checked against the schema
  ↓
SQLite
```

Back up the same path, one thing matters: the server encodes with
`commerce_shared` and the client decodes with `commerce_shared`. The models are
not similar, they are the same classes. A field renamed once is a compile error
at both ends.

## What is generated

| Layer | Generated | Hand-written |
| :--- | :--- | :--- |
| `commerce_shared` | data classes, JSON, validation | the model definitions |
| `commerce_server` | row mapping, DAOs, SQL validation | routing, handlers, services |
| `commerce_app` | routing, view models, i18n, the API client | widgets |

**There is no server code generator in Dust.** Handlers are written against
`dust_server`'s API directly. This is worth saying plainly because the fixture
in Dust's own repository contains files with a `// Generated by dust.` header
that are hand-written — its pubspec says so — and reading them the wrong way is
how this project first mis-stated its own architecture.

## Decisions that would be expensive to reverse

### Money is an integer, everywhere but the last inch

`Money` holds a count of a currency's minor unit. It is divided by a hundred in
exactly one function, `formatMoney`, at the edge of the UI. A binary fraction
cannot represent a decimal one, and the error compounds across a cart.

Tax rounds half away from zero. Dart's `~/` truncates, which under-collects on
every line of every order once a rate lands on a fraction of a minor unit — and
at 8.75% of 1999 it does.

### The variant carries price and stock, not the product

A medium black shirt and a large black shirt are different things to count and
ship. A model that prices the product cannot say that. This is Medusa's shape
and the main reason its model was worth following.

### A line snapshots its price

A cart that reads today's price when it renders silently rewrites what someone
agreed to, and the first they know is the total moving between page loads. The
snapshot is taken when the line is added and never read again. There is a test
that reprices a variant in the database mid-cart and asserts the line does not
move.

### An order stores its totals

Every amount on an order is written, not derived. An order recomputed from
today's prices, tax rates, or catalogue would change what a customer was
charged months after they were charged it. Order lines and addresses are copied
rather than referenced for the same reason: editing an account's address must
not rewrite where something was already shipped.

### Stock is taken by a conditional UPDATE

Two checkouts racing for the last unit both read "one left". Only the write can
decide between them, so the check lives in the `WHERE` clause and a zero row
count is how the loser finds out. Inside the transaction, stock is taken before
the order is written: a sold-out line then fails before an order exists.

### Filters live in SQL

Draft products are excluded by the query, and orders are scoped to an email by
the query. A filter in Dart is one forgotten line away from showing somebody
else's data; a filter in SQL cannot be forgotten by a caller.

## Layers that were harder than expected

Three Dust behaviours shaped the code and are reported upstream:

- [dust#536](https://github.com/y3l1n4ung/dust/issues/536) — an enum used across
  library boundaries serialises to a scalar and deserialises expecting a map.
  `ProductStatus` therefore lives beside `Product` rather than in its own file.
- [dust#537](https://github.com/y3l1n4ung/dust/issues/537) — a `@Query` whose
  SQL ends on a quote generates uncompilable Dart while the build reports
  clean. `countPublished` is written across several lines to avoid it.
- [dust#538](https://github.com/y3l1n4ung/dust/issues/538) — `validate()` does
  not cascade into nested annotated objects, so an address with an empty
  recipient passed the outer check and produced an unshippable order.
  `checkout/validation.dart` cascades by hand.

## Verifying

CI runs what a contributor should run: `dust check` proves committed generated
files match their sources, `dust check --db` validates every query against the
real schema, `dust i18n check` catches drifted translations, and
`scripts/check_file_size.sh` enforces the 180-line rule. All exit non-zero on
failure, which was tested rather than assumed.

Do not run `dart format` across a package — see [CONTRIBUTING](../../CONTRIBUTING.md).
