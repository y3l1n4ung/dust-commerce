# Admin customer-group detail QA

## Scope

This vertical slice implements Medusa-compatible customer-group detail under
issue [#33](https://github.com/y3l1n4ung/dust-commerce/issues/33). It includes
the standalone Admin contract, guarded server read, group-scoped customer query,
generated Dio and Dust state, source-shaped Flutter route and release-browser
QA. No widget test or schema migration was added.

## Pinned Medusa comparison

The source target is Medusa commit
`bda24b9725ac697ec5e8f706b503013e20babf12`.

`customer-group-detail.tsx` composes the General, Customers, Metadata and JSON
sections in one column. `customer-group-general-section.tsx` displays the group
name and active customer count. `customer-group-customer-section.tsx` requests
10 group-scoped customers and provides search, filtering, ordering, paging and
customer navigation. `use-customer-table-query.tsx`, `constants.ts` and
`en.json` define the query boundary, detail fields and visible empty copy.

The Flutter route preserves that hierarchy and exact
“This group doesn't have customers.” copy. Mutation controls are intentionally
absent until their guarded operations exist, rather than rendering fake Edit,
Delete, Add or Remove actions.

## Contract and server behavior

`AdminCustomerGroupDetail` is a standalone response allowlist, not a database
model subclass. It exposes id, name, active customer references, nullable
metadata and `DateTime` audit fields. The Medusa-shaped response envelope is
generated by Dust and pins the exact serialized keys.

`GET /admin/customer-groups/{id}` uses the parent Admin guard and explicitly
extracts `AuthenticatedAdmin`. Its SQLx row directly decodes the response,
including ordered active customer ids and JSON metadata. Missing and
soft-deleted groups share a `404`; the service exposes one flat
`Result<Option<...>, SqlxError>`.

`GET /admin/customers?groups={id}` applies active group and membership checks
inside both list and count SQL before the existing search, account, date,
ordering and paging boundary. Unknown or deleted groups return an empty page.

## Admin behavior

The generated group client owns no bearer parameter because the process Dio
interceptor attaches authorization. Dedicated state uses `Option` for the
selected group and failures, while customer loading, query, filters, ordering
and paging remain independent so a customer-section failure cannot discard the
loaded group.

List rows and successful creation open the group detail route. Working controls
include search, registered/guest filtering, all customer ordering choices,
10-row paging and customer-row navigation. Metadata renders real key/value data,
and JSON contains only the explicit Admin allowlist.

## Live browser evidence

API `3878` and a fresh release Admin build on `13002` used the existing
SQLx-history-matching disposable database with 13 groups and multiple customers.

Authenticated browser QA verified:

- selecting `VIP Customers` from the real group list opens its detail route;
- the title, General customer count, Customers, Metadata and JSON sections load;
- the customer table returns Ada and Grace through the group filter;
- searching `ada` changes the server-owned count from two to one;
- the Guest filter produces the exact empty state and restoring All retains the
  active search;
- clearing search restores both members;
- selecting Ada opens the existing customer-detail route;
- the default compact viewport remains usable;
- `1440 x 1000` preserves the source single-column hierarchy; and
- the browser console reports no warning or error.
